## 实验一：完整 MoE 模型训练仿真与物理链路带宽分析

### 1.1 实验目标
在 **Rail-Optimized** 64 卡 H100 数据中心拓扑上，模拟大规模 MoE 模型的分布式训练通信过程，评估 Leaf-Spine 层（ASW 与 PSW 交换机之间）的物理链路吞吐量、负载均衡度与队列积压（Bandwidth & Queue Length）。

---

### 1.2 完整步骤与命令

#### 步骤 1：生成 MoE 训练通信 Workload
利用 AICB 工具根据大模型并行策略配置（32 卡、TP=2、PP=1、EP=16、64 专家、Top-2 路由）生成通信算子流。

- **执行位置**：`aicb/` 目录
- **执行命令**：
  ```bash
  python3 -m workload_generator.SimAI_training_workload_generator \
    --world_size=32 \
    --global_batch=64 \
    --micro_batch=1 \
    --num_layers=2 \
    --num_attention_heads=32 \
    --hidden_size=4096 \
    --tensor_model_parallel_size=2 \
    --pipeline_model_parallel=1 \
    --expert_model_parallel_size=16 \
    --num_experts=64 \
    --moe_router_topk=2 \
    --moe_enable \
    --seq_length=4096 \
    --swiglu \
    --use_flash_attn \
    --enable_sequence_parallel
  ```
- **输入依赖**：AICB 生成器配置文件
- **产出文件**：[None-None-world_size32-tp2-pp1-ep16-gbs64-mbs1-seq4096-MOE-True-GEMM-False-flash_attn-True.txt]（位于 `workloads/` 目录下）

---

#### 步骤 2：生成 Rail-Optimized 拓扑文件
生成包含 64 张 H100 GPU（8 卡/节点，400Gbps 网卡）、ASW 交换机和 PSW Spine 交换机的 Rail-Optimized 物理网络架构。

- **执行位置**：项目根目录
- **执行命令**：
  ```bash
  python ./astra-sim-alibabacloud/inputs/topo/gen_Topo_Template.py --ro -g 64 -gps 8 -gt H100 -bw 400Gbps -psn 8
  ```
- **输入依赖**：拓扑生成模板脚本
- **产出文件**：[Rail_Opti_SingleToR_64g_8gps_400Gbps_H100]（位于 `topos/` 目录下）

---

#### 步骤 3：运行 SimAI 仿真引擎
将 MoE Workload 与 Rail-Optimized 拓扑送入 SimAI 仿真器进行多线程离散事件仿真。

- **执行位置**：项目根目录
- **执行命令**：
  ```bash
  ./bin/SimAI_simulator \
    -t 8 \
    -w ./workloads/None-None-world_size32-tp2-pp1-ep16-gbs64-mbs1-seq4096-MOE-True-GEMM-False-flash_attn-True.txt \
    -n ./topos/Rail_Opti_SingleToR_64g_8gps_400Gbps_H100 \
    -c ./astra-sim-alibabacloud/inputs/config/SimAI.conf
  ```
- **输入依赖**：
  - `-w`: Workload 文件
  - `-n`: 拓扑文件
  - `-c`: SimAI 配置文件
- **产出文件**：
  - `results/data/Analytical_Sim.log`（仿真逻辑日志）
  - `results/data/ncclFlowModel_detailed_72.csv`（交换机端口底层 Trace 日志）
  - `results/data/ncclFlowModel_EndToEnd.csv` / `ncclFlowModel_test1_dimension_utilization_0.csv`

---

#### 步骤 4：物理链路吞吐量与队列分析绘图
解析物理 Trace 数据，画出 ASW 节点（如 Node 72）到各个 PSW 节点（如 Node 80~83）物理链路的时序吞吐量（Gbps）与队列积压。

- **执行位置**：项目根目录
- **执行命令**：
  ```bash
  # 绘制 Node 72 (ASW) <--> Node 80 (PSW) 链路带宽（采样窗口 100us）
  python scripts/analysis/plot_link_bandwidth.py \
    results/data/ncclFlowModel_detailed_72.csv \
    topos/Rail_Opti_SingleToR_64g_8gps_400Gbps_H100 \
    72 80 100.0 \
    results/plots/link_72_80.png

  # 终端文本分析特定端口最大队列积压 (Max Queue Length)
  python scripts/analysis/analyze_link.py \
    results/data/ncclFlowModel_detailed_72.csv \
    72 0 100
  ```
- **输入依赖**：`ncclFlowModel_detailed_72.csv` Trace 文件 + 拓扑文件
- **产出文件**：
  - [link_0_72.png]
  - [link_72_80.png]
  - [link_72_83.png]

## 实验二：简化 Workload 仿真与逻辑 Flow 依赖图分析

### 2.1 实验目标与改造动机
在分布式错峰调度研究中，需要在第二阶段（自研 Python 模拟器）中回放真实 NCCL 算子的 Flow 依赖有向图（Flow DAG）。然而开源 SimAI 默认的三种模式均存在局限：
1. **纯 Python 模拟（mock_ccl.py）**：过于简陋，无法还原真实 NCCL 的多通道（nChannels）、Tree/Ring 自适应算法及硬件特性。
2. **原始 Analytical 模式（ModeType::ANALYTICAL）**：仅用代数公式快速计算时间，**完全跳过了 FlowModels 生成**，日志中没有任何 Flow Chunk 依赖信息。
3. **原始 ns-3 模式（ModeType::MOCKNCCL）**：能生成正确的 Flow DAG 日志，但依赖庞大的物理网络仿真（ns-3），**编译和运行速度极慢**。

#### 💡 C++ 源码改造方案：构建“零延迟 Mock 网络”生成器
为了同时获得 **Analytical 模式的毫秒级极速** 与 **ns-3 模式的 Flow DAG 正确性**，对 SimAI 源码（`astra-sim-alibabacloud`）进行了关键改造：
1. **解除编译宏限制**：从 `CMakeLists.txt` 中移除 `-DANALYTI`，恢复通信层的真实推导逻辑。
2. **解除初始化宏限制**：修改 `Sys.cc`，使 `mock_nccl_grobal_group_init()` 在非 ns-3 编译下也能正常初始化，防止空指针段错误。
3. **切换运行模式**：在 `AnalyticalAstra.cc` 中将运行模式强制设为 `param->mode = ModeType::MOCKNCCL`，触发真实的 MockNCCL 拓扑切分与 DAG 生成。
4. **改造模拟网络为“零延迟 (Zero-Delay)”**：修改 `AnalyticalNetwork.cc` 中的 `sim_send` / `sim_recv`，设置 `delay.time_val = 0`，数据包不进行物理排队，发送后在下个 tick 立即回调。

使得程序能在**毫秒级内跑完整层 Workload，并输出包含 `parent_flow_id` 与 `child_flow_id` 的白盒 `Analytical_Sim.log`**。

---

### 2.2 完整步骤与命令

#### 步骤 1：构造精简 Workload
使用精简的单 Step / 单层通信序列描述文件（如 `simplified_workload.txt`），便于清晰追踪流依赖。

- **输入依赖**：手工定义或裁剪后的通信描述文件
- **产出文件**：[simplified_workload.txt](file:///c:/Users/jinha/Desktop/testPytorch/SimAI/workloads/simplified_workload.txt)（位于 `workloads/` 目录下）

---

#### 步骤 2：运行改造后的“零延迟”Analytical 仿真器生成 Flow DAG
编译并运行改造后的 Analytical 二进制程序（`SimAI_analytical`），以零物理网络延迟在毫秒级内完成离散推演，输出无乱序、无多线程交错的白盒 Flow 日志。

- **执行位置**：项目根目录
- **执行命令**：
  ```bash
  # 运行改造后的 Analytical 极速流图生成器（无需 -n 指定物理拓扑）
  ./bin/SimAI_analytical \
    -g 64 \
    -g_p_s 8 \
    -g_type H100 \
    -w ./workloads/simplified_workload.txt
  ```
  *(注：`./bin/SimAI_simulator` 对应的是 ns-3 物理网络包仿真器，而改造后的零延迟 Mock 网络生成器对应的可执行文件是 `./bin/SimAI_analytical`。它内部通过 `MockNcclGroup` 程序化构建拓扑，因此无需 `-n` 物理拓扑文件，也不存在多线程日志乱序问题)*
- **输入依赖**：`simplified_workload.txt`
- **产出文件**：`results/data/Analytical_Sim.log`（包含各 Channel/Chunk 的 `current_flow_id`, `parent_flow_id`, `child_flow_id` 依赖日志）

---

#### 步骤 3：转换与结构化 Flow 日志
提取并清洗 `Analytical_Sim.log` 中记录的 Flow 节点依赖关系，导出为标准的结构化文本表格。

- **执行位置**：项目根目录
- **执行命令**：
  ```bash
  python scripts/analysis/convert_log.py \
    -i results/data/Analytical_Sim.log \
    -o results/data/gpu_flows_parsed.txt
  ```
- **输入依赖**：`results/data/Analytical_Sim.log`
- **产出文件**：[gpu_flows_parsed.txt]包含 `flow_id,src,dst,size,channel_id,chunk_id,parent_flow_id,child_flow_id` 数据）

---

#### 步骤 4：绘制 GPU 流量依赖关系图 (Flow Dependency Graph)
读取解析后的 Flow 描述文件，利用 `networkx` 构建拓扑依赖有向图（DiGraph），渲染为交互/可视化图像。

- **执行位置**：项目根目录
- **执行命令**：
  ```bash
  # 1) 绘制 GPU 0 在所有 Channel 上的整体 Flow 依赖图
  python scripts/analysis/visualize_flows.py \
    --input results/data/gpu_flows_parsed.txt \
    --gpu 0 \
    --output results/plots/flow_dep_gpu0.png

  # 2) 仅绘制 GPU 0 在 Channel 0 上的细粒度 Flow 依赖图
  python scripts/analysis/visualize_flows.py \
    --input results/data/gpu_flows_parsed.txt \
    --gpu 0 \
    --channel 0 \
    --output results/plots/flow_dep_gpu0_ch0.png

  # 3) 绘制所有 GPU 在 Channel 0 上的跨节点 Flow 依赖图
  python scripts/analysis/visualize_flows.py \
    --input results/data/gpu_flows_parsed.txt \
    --channel 0 \
    --output results/plots/flow_dep_allgpus_ch0.png
  ```
- **输入依赖**：`results/data/gpu_flows_parsed.txt`
- **产出文件**：
  - [flow_dep_gpu0.png]
  - [flow_dep_gpu0_ch0.png]
  - [flow_dep_allgpus_ch0.png]

## 分析脚本工具说明 (`scripts/analysis/`)

| 脚本名称 | 功能描述 | 输入 | 核心输出 |
| :--- | :--- | :--- | :--- |
| [analyze_link.py] | 解析二进制/CSV Trace 日志，统计指定 Node/Port 的 Max Queue Length 及时间窗口带宽。 | 物理 Trace 文件 (`.tr`/`.csv`) | 终端数据分析报告 |

| [plot_link_bandwidth.py] | 根据拓扑结构自动定位 Node U <-> Node V 的端口号，绘制双向物理链路带宽随时间变化折线图。 | Trace 文件 + 拓扑文件 | 带宽折线图 (`link_*.png`) |

| [convert_log.py] | 从 `Analytical_Sim.log` 正则提取 NCCL Flow 依赖链（Channel, Chunk, Parent/Child Flow ID）。 | `Analytical_Sim.log` | `gpu_flows_parsed.txt` |

| [visualize_flows.py] | 构建 Flow 有向依赖图（DiGraph），按照 GPU Rank / Channel / Chunk 轴渲染流依赖图。 | `gpu_flows_parsed.txt` | 流量依赖图 (`flow_dep_*.png`) |

| [visualize_topo.py] | 可视化数据中心物理拓扑与 Ring AllReduce / EP Cross-Rail 通信路径。 | 拓扑描述/策略配置 | 拓扑与路径示意图 |
